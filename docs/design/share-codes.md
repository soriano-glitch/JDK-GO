# Share codes

> 2026-10-24. Turn a plugin or a DSH configuration into a link / QR code / file; when the other person opens it they see a confirmation sheet and install it in one step into the DSH on their phone or the remote DSH they are connected to. There is no backend: a link either points to a public source (npm / GitHub) or carries its content itself.

Where the code is:

| Part | Files |
|---|---|
| App link infrastructure | `app/lib/links/app_links.dart`, `android/.../links/LinksPlugin.kt`, `LinkTrampolineActivity.kt`, `AndroidManifest.xml` |
| Encoding/decoding, format validation | `app/lib/share_code/share_codec.dart`, `share_models.dart`, `share_link.dart` |
| Export / import | `profile_export.dart`, `settings_sanitizer.dart`, `share_import.dart`, `restore_point.dart`, `guest_fs.dart`, `share_net.dart` |
| Sheets | `app/lib/ui/share_code/` |
| Landing page | `site/share/index.html`, `site/share/share.js` |

## 1. Links

| Form | Example | Used for |
|---|---|---|
| App link | `dshgo://share/<kind>?p=<code>` | Opening directly between apps |
| Large configuration | `dshgo://share/profile?gist=<id>&c=<sum>` | Content placed in a private Gist |
| Landing page | `https://go.dshtui.com/share/#p=<code>`, `…/#gist=<id>&c=<sum>` (the old address `https://ccch1mneyyy.github.io/dsh-go/share/` still opens) | Copy link, QR code, sending to WeChat |
| File | `dsh-go-profile-20261024.dshgo` (`application/vnd.dshgo+json`) | Share panel, save as file, forwarding in WeChat |

- `<kind>`: `plugin` / `profile` / `conversation` (for conversations see §8; the link is hosted, not inlined). A landing-page link carries no kind, which is known only after decoding.
- All the landing page's content is after `#`: the browser doesn't send it to the server.
- Changing domains: change `shareLandingUrl` in `share_link.dart`; `site/share/share.js` contains no domain (it only recognizes relative paths); for App Links see §6.
- "Copy link", "QR code" and "Share" all use the landing-page link: WeChat doesn't open custom schemes, https can be tapped anywhere, and "Open with dsh-go" on the landing page then jumps to `dshgo://`.

## 2. Encoding

```
<code> = base64url(deflate-raw(JSON)) "." base64url(SHA-256(JSON)[0..6])
```

- The JSON is compact UTF-8; the checksum covers the decompressed JSON bytes, so truncation and edits are detected ("This share code is incomplete or damaged").
- `v` is the format version, currently 1; a version newer than the app is rejected ("Update dsh-go to open this").
- The decompression limit is 1 MB (against compression bombs). A landing-page link ≤ 1800 characters is inlined, and the QR code uses L-level error correction (> 600 characters) or M-level, with no center icon (reasons in "QR center icon" in community.md); larger configurations go via a file or Gist.
- `.dshgo` files and Gists hold the same code, wrapped in a readable header: `{"dshgo": 1, "kind": "profile", "name": "…", "code": "<code>"}`. One decode path.
- The landing page uses `DecompressionStream('deflate-raw')` and `crypto.subtle` to decode the same format. Codes generated by Python (zlib + hashlib) can be decoded in the Dart tests; codes generated by Dart were run through the landing-page script with Node (manually verified, not in the tests).

## 3. Content

### Plugin (`kind: plugin`)

```json
{"v":1,"kind":"plugin","plugin":{"name":"@acme/dsh-notes","source":"npm","spec":"@acme/dsh-notes@1.4.2",
 "version":"1.4.2","integrity":"sha512-…","title":"Reading notes","author":"Acme","summary":"…"}}
```

A link can install only these kinds, validated strictly when read:

| source | spec | Notes |
|---|---|---|
| `npm` | Must equal `name@<exact version>` | `integrity` takes npm's `dist.integrity` (at export time from registry.npmjs.org, asking npmmirror if it can't answer) |
| `github` | `github:owner/repo#ref[&path:/dir]` or `git+https://github.com/…#ref` | DSH's installer (pnpm) accepts these two |
| `git` | `git+https://<host>/…#ref[&path:/dir]` | Only https is recognized |
| `official` | None | DSH's built-in optional plugin; on import it is merely opened |

Local paths, `file:`, `link:`, tarballs and `git+ssh` can never be shared (the list shows "Installed locally, can't be shared"). Display text is truncated, newlines removed, and used as text only.

### Configuration (`kind: profile`)

```json
{"v":1,"kind":"profile","name":"…","created":"…Z",
 "settings":{"subagent":{"maxDepth":3}},
 "plugins":[…], "presets":[{"id":"writer","name":"Writing","bundle":"@acme/dsh-notes"}],
 "skills":[{"name":"outline","files":{"SKILL.md":"…"}}], "agentsMd":"…"}
```

- **Settings**: each namespace (the ns of `settings/describe`) takes only the **user layer** (`user`, not the composed value). Sanitizing rules (`settings_sanitizer.dart`):
  - Account, credential, telemetry and network-listening namespaces don't appear at all (names containing account / credential / telemetry / analytics / remote-access / webserver / gateway / auth …);
  - Fields the schema marks `secret` and slots listed in `secrets` are removed (the Host doesn't return values anyway); fields marked `credential-ref` are kept — it's only the **name** of a credential;
  - Fields whose names end with token / secret / password / cookie / authorization / apiKey (or `api/private/client…` + `key`) are removed, while ones like `maxTokens`, `apiKeyEnv` and `keyId` are kept;
  - Values that look like secrets (the same recognition as masking credentials in chat: `sk-…`, `ghp_…`, JWT, private-key blocks…), long random tokens, `Bearer …`, URLs with credentials or parameters like `token=`, or absolute local paths (`/…`, `~/…`, `C:\…`, `file:`) are removed; objects / arrays emptied by deletion are removed too.
- **Plugins**: installed third-party plugins by exact version, plus enabled official optional plugins.
- **Presets**: agent presets can only be declared by plugins (the Host has no interface to write presets), so presets follow the plugin that declares them: only when the plugin is selected are its presets in; on import the preset rows follow the plugin's switch.
- **Skills**: read only from the local engine (`/root/.dsh/skills`, `/root/.agents/skills`), with the small text files in the folder coming along (≤ 12, each ≤ 64 KB, no hidden files or binaries).
- **AGENTS.md**: the personal preferences on this device (use `/root/.dsh/AGENTS.md` when it isn't the app-managed one, otherwise `/root/.agents/AGENTS.md`). **Unticked** by default.

All text files in skills and personal preferences are scanned with the chat credential-recognition rules; an item that hits a secret is shown as "Contains a secret, can't be shared" and isn't added to the shared content. Variable references like `Bearer $TOKEN` aren't treated as secrets.

Each row of the export list is marked with its size (JSON bytes), and the bottom says "N items selected · can generate a QR code / share as a file".

## 4. Opening and importing

Entry points: `dshgo://share/…`, landing-page links (after App Links verification), and `.dshgo` files (the file manager's "Open with", or "Share" to dsh-go from WeChat, with `application/vnd.dshgo+json` and `application/octet-stream` for VIEW / SEND in the Manifest). These intent filters hang on the UI-less `LinkTrampolineActivity`: when an app like WeChat launches without `NEW_TASK`, hitting `MainActivity` directly would start another Flutter UI inside WeChat's task; the trampoline forwards the link into the app's own task (`NEW_TASK | SINGLE_TOP | CLEAR_TOP`, together with read permission for `content:`), and `LinksPlugin` hands it to Dart via `onNewIntent` or the launch intent. `ShareCodeHost` registers with `LinkRouter` at startup, so a link brought in by a cold start can be caught too.

The confirmation sheet (`import_sheet.dart`):

- **What it is**: the plugin icon, name and description; the configuration's name and "3 plugins · 5 settings · …".
- **Source**: npm · publisher (the registry's `_npmUser`) / GitHub · owner/repo / host name / share link, file, GitHub Gist.
- **Verification**: for an npm plugin, the registry's current `dist.integrity` is compared with the one in the link — a match shows "Verified", a mismatch "Verification mismatch" (the plugin can't be installed), and if it can't be fetched or the source is git, "Can't verify". The configuration's checksum only detects content integrity and doesn't show "Verified".
- **Size**: for a plugin it is npm's `unpackedSize`, and for a configuration the content size.
- **Where to install**: this phone (when the engine is running) and the currently connected remote host; with both present it's a segmented capsule, and switching re-compares.
- **Changes** (configuration): plugins (install / update 1.2.0 → 1.4.2 / enable / no change needed), presets (added with a plugin), settings (one row per namespace, `maxDepth 1 → 3`, those already the same aren't shown; ones not yet on the target but where a plugin will be installed this time are written "Apply after the plugin is installed"), skills (unticked by default; same name with different content is "Replace the same-named skill"), personal preferences (unticked by default, and when replacing it states "Replaces existing content"). Each row has a round tick; ones that can't be done state why ("Can only be imported to this phone", "This host can't install plugins from here", "Plugins can't be installed in safe mode").
- **Installation**: in order — restore point → plugins (when the target is the current host it goes through the same install queue as the plugin page, `pluginInstallsProvider`, with progress visible on the plugin page too; otherwise it directly calls that host's `pluginManager/*`) → `settings/describe` again, then `settings/mutate` namespace by namespace (with `expectedRevision`) → skills → AGENTS.md. Each row spins / ticks / errors live; when a restart is needed the phone offers "Restart engine", and for remote it writes "Takes effect after restarting DSH on …".

### Confirmation of settings and text

- Namespaces that must not be shared, such as accounts, authentication and network listening, are dropped when the share code is parsed.
- Schema secrets, secrets slots and secret field names generate no write operations; nested objects are shown and written by dotted path, and an array containing a secret field is skipped as a whole item.
- Model, permission and sandbox namespaces, credential references, and fields whose names end with URL / URI / endpoint / host / proxy / registry are sensitive settings, whose whole rows are unticked by default. Sensitive fields are shown first, with addresses keeping the complete host and path, not folded into "and N more".
- When a plugin isn't installed, "Apply after the plugin is installed" and the specific changes are shown; when reading settings fails, all settings rows are unselectable.
- Skills and personal preferences are unticked by default; tap "View" to read the full file first and then decide whether to import.

### Restore point

Before importing a configuration locally, the main configuration's current state is written as a "last known good configuration" record (`filesDir/runtime/lkg/lkg.json`, in the same format as `LastKnownGood.kt`'s `load` / `save`: enabled composition bundles, installed packages and versions, the `cordis.patch.yml` settings layer). So if something goes wrong after the import, "Restore last known good configuration" in safe mode returns to before the import; if the imported configuration itself runs healthy for a full two minutes after restart, native code records it as the new "last known good" as usual. Skills and AGENTS.md aren't in that record: replaced files are first copied to `/root/.dsh/backups/share-import-<time>/` (not the skills root, so they won't be loaded). The AGENTS.md backup directory gets a unique suffix after the time, so each import keeps its own, to avoid overwriting an old backup when importing again within the same second.

Remote hosts have no restore point (safe mode is a local feature).

## 5. Landing page

`site/share/`: one `index.html` (inline styles) + `share.js`, no build. It reads `#p=` / `#gist=`, decompresses and verifies in the browser, and shows a card (name, source, version, what's inside), with two buttons: "Open with dsh-go" (`dshgo://…`) and "Download dsh-go" (`github.com/ccch1mneyyy/dsh-go/releases/latest`). Light / dark follows the system.

- Uploads nothing; the CSP allows only its own scripts, and `connect-src` is only the GitHub API (Gist links need to fetch the Gist). All data is written into the page with `textContent`.
- WeChat's built-in browser can't open custom schemes: when detected it prompts to open in a browser.
- When the browser doesn't support `DecompressionStream`, no content is shown, and "Open with dsh-go" is still given.

## 6. App Links (https straight into the app)

Currently only `dshgo://` and files can go straight into the app; https links go to the landing page first. To make `https://<domain>/…/share/` open the app directly:

1. Settle the domain and change `shareLandingUrl`;
2. At `https://<domain>/.well-known/assetlinks.json` put `delegate_permission/common.handle_all_urls`, `package_name: io.github.ccch1mneyyy.dsh_app`, and `sha256_cert_fingerprints` with the fingerprint of the release signing certificate (GitHub Pages project pages can't do this — `.well-known` must be at the domain root, so use the `ccch1mneyyy.github.io` user site or your own domain);
3. In the Manifest add to `LinkTrampolineActivity` an `<intent-filter android:autoVerify="true">`: VIEW + DEFAULT + BROWSABLE, `scheme="https" host="<domain>" pathPrefix="/…/share"`.

`LinkRouter` already registers the landing-page route by `<host>/<path>`, so no Dart change is needed after step 3.

## 7. How other features hook into links (`app/lib/links/app_links.dart`)

```dart
final router = ref.read(linkRouterProvider);
final off = router.registerLinkHandler('forum/auth', (uri) async { …; return true; });
router.registerFileHandler('dshgo', (fileUri) async => …);
router.context; // A BuildContext under the home route, for opening sheets
```

- Routing is by host (with an optional path prefix, longest match first); the host of an https link is the URL's host. Returning false or throwing → "Can't open this link".
- Each link is dispatched only once, including the cold-start one; links that arrive before the home shell appears are queued; a link with no handler waits at most 4 seconds (counted from the home shell's first appearance), so handlers should be registered at startup (a widget in the home shell or a provider it reads), not waiting for a page to open.
- Reserved hosts: `share` (share codes), `forum` (community login).

## 8. Conversation files and replay

> 2026-10-25. Share a conversation: when the other person opens it with dsh-go they can replay it and continue chatting; people without the app can view it in a browser. The three forms share one file: a `.dshgo` file, a self-contained `.html`, and a hosted link (end-to-end encrypted).

| Part | Files |
|---|---|
| Format, encoding/decoding, images | `app/lib/share_code/conversation_share.dart` |
| Export from chat | `conversation_export.dart`, `conversation_redact.dart`, `image_shrink.dart`, `jpeg_encoder.dart` |
| Self-contained web page | `conversation_html.dart`, `replay_viewer.g.dart` (generated) |
| Replay page | `app/lib/ui/replay/` (`replay_timeline.dart`, `replay_frame.dart`, `replay_list.dart`, `replay_page.dart`, `continue_chat.dart`) |
| Share panel | `app/lib/ui/share/share_panel.dart`, `share_panel_pages.dart`, `ui/replay/conversation_out.dart` (see [share-redesign.md](share-redesign.md)) |
| Web viewer | `site/share/viewer.js`, `viewer.css`, `viewer.html` (page skeleton), built by `app/tool/make_replay_viewer.py` |

### 8.1 Format

The file's outer layer is the same readable envelope as §2, with `assets` added:

```json
{"dshgo": 2, "kind": "conversation", "name": "Fix duplicate login submission",
 "code": "<base64url(deflate-raw(body))>.<sum>",
 "assets": {"<id>": {"type": "image/jpeg", "w": 1600, "h": 900, "data": "<base64>"}}}
```

- The body inside `code` uses §2's encoding; `v: 2`. Plugins / configurations still write `v: 1`, so an old app reading a conversation says "update needed" rather than "damaged". The body decompression limit is 16 MB (plugins and configurations are still 1 MB).
- Images don't go into the body but into `assets`, named by content: `id` = base64url(first 9 bytes of SHA-256(bytes)), 12 characters. They're verified one by one when read, mismatched images are dropped and the rest open as usual; images the body doesn't use aren't written.
- The whole file is limited to 4 MB (`maxConversationFileBytes`, the upper bound Android's "Open with" can hand to the app, `LinksPlugin.kt`).

The body is a **normalized schema**, not DSH's raw events, and both the app and the web recognize only it:

```json
{"v": 2, "kind": "conversation", "schema": 1,
 "title": "…", "model": "deepseek-v4-pro", "app": "dsh-go 1.0.0",
 "created": "…Z", "start": "…Z",
 "range": {"from": 2, "to": 3, "of": 5},
 "include": {"thinking": false, "tools": true},
 "entries": [ … ]}
```

- `start` is the time origin; each entry's `t` is the milliseconds relative to it, and `d` is the duration in milliseconds (may be absent). `range` appears only when part is shared; `include` appears only when reasoning or tool output has been removed.
- `schema` is the version of this structure. Adding fields or entry types doesn't raise the version (readers skip types they don't know); it is raised only when meaning changes, and old readers reject it and prompt for an update.

| `type` | Fields | Notes |
|---|---|---|
| `turn` | `t` `d` `end` `steps` `tokens` | The start of a turn (placed before its question, consistent with the order DSH logs); `end` is the end reason, and none = still running at export |
| `user` | `text` `images[{id,w,h,name}]` `files[{name,size}]` `source` | The question; files carry only name and size; `source` appears only when it wasn't sent by a person (`goal`, `schedule`) |
| `reply` | `t` (first token) `d` (streaming duration) `think` `text` `plain` `model` `cut` | `text` is the Markdown the app renders (including visual replies); `plain` is the version with visual blocks replaced by a one-line summary, appearing only when there are visual blocks, for the web |
| `tool` | `name` `args` `summary` `verb` `status` `result` `more` `error` | `status`: `ok` `failed` `denied` `cancelled`; `summary` / `verb` are the line of text on the app's tool row; `result` keeps head and tail with the middle truncated, and `more` is the number of characters cut |
| `notice` | `kind` `text` | Errors, stopped, retries… |
| `todos` | `items[{text,status}]` | The to-do list is replaced as a whole; cleared at the start of the next turn (consistent with the DSH projection) |
| `goal` | `text` `phase` | `text` absent = goal cleared |
| `command` | `line` `ok` `text` | Slash commands and results |

Why it's defined this way: app replay needs to restore entries into chat's own rows (`ChatItem` / `TurnTrace`), so tool arguments, turn start/end and step counts are kept; the web has no app tool views or visual rendering, so at export "the tool row's line of text" and "the visual summary" are precomputed and put in. Both sides therefore see the same thing, while signatures, request headers and subagent details in the raw events are never carried.

### 8.2 Export

Entry: the share panel's ([share-redesign.md](share-redesign.md)) "Link", "File" and "Text". The share key below a reply, the long-press menu, the drawer and replies within replay all open it (`share_entry.dart`).

- First read the whole history fully (`loadOlder` to the end), then read the images out and shrink them once (long side ≤ 1600; PNG / JPEG / WebP that are already small enough are kept as is, transparent images converted to PNG, others encoded as pure-Dart JPEG q82).
- Scope: this reply (and the question above it), the selected messages, the whole conversation (`ConversationExport.build(only:)`). When messages are selected, only the selected questions and replies are taken, and tools, to-dos and goals only for the turn the selected replies belong to; `range` records the turns covered. One turn = from one question to before the next question; a turn's start takes that turn's `turn/start`.
- Include: reasoning, tool calls (when off, the whole call along with arguments, results, to-dos and goals is not carried), images (when off, references to question images and the assets don't enter the file). Masking always happens (§8.3).
- Preview: opened with the same replay page the recipient sees (without "Continue chat").
- File forms: the conversation file `.dshgo`, web page `.html`, Markdown (the digest used by "Continue chat", without reasoning and tool output).
- Over 4 MB (conversation file, web page, link): a line "Over 4 MB, please narrow the scope", and the button is disabled.

### 8.3 Masking (`conversation_redact.dart`)

Every piece of text going into the file passes through — messages, reasoning, tool arguments and output, notices, to-dos, goals, file names:

- Credentials: the recognition used for masking in chat (`sk-…`, `ghp_…`, JWT, private-key blocks, passwords in URLs), plus "assignments whose names look like secrets" (`API_KEY=…`, `"password": "…"`), with placeholders like `$VAR` and `<token>` left alone;
- Home directories: `/home/<name>`, `/Users/<name>`, `C:\Users\<name>` → `~`. `/root` is kept: it's what every phone engine uses and identifies no one;
- The app's private directories `/data/user/0/<package>`, `/data/data/<package>` → `…`;
- Images in replies `![alt](…)` are replaced by `〔alt〕`: the viewer makes no requests, and a local path means nothing elsewhere.

### 8.4 Web viewer

One source (`site/share/viewer.js` + `viewer.css`), three sources, decided by `DshgoViewer.boot()`:

| Source | Page | Where the data comes from |
|---|---|---|
| Local file | Landing page `index.html` (when there are no `#` parameters) | Choose or drag in a `.dshgo` |
| Self-contained web page | The `.html` exported by the app | `<script type="application/json" id="dshgo-data">` in the page |
| Hosted link | The share domain's `/c/<id>` (the built `c.html`) | `GET /api/v1/c/<id>`, decrypted with `#k=` |

`app/tool/make_replay_viewer.py` inlines the source into two pages: `replay_viewer.g.dart` (the app fills in the title and data, `connect-src 'none'`) and `<out>/c.html` (`connect-src 'self'`), and also copies the landing page files into `<out>/` (default `site/build/share/`, published by the share service). Inline scripts are locked with CSP hashes; data enters the page only as text nodes and `data:` images; the embedded JSON escapes `<` `>` `&`. `test/share_code/replay_viewer_sync_test.dart` checks the generated files agree with the source; `node site/share/test/viewer_test.mjs` checks the web's decoding, verification and decryption, and that the replay pacing matches the app item by item (sharing `app/test/replay/fixtures/timeline.json`).

Markdown and code highlighting are the viewer's own lightweight implementation (headings, lists, quotes, tables, code blocks, inline formatting, links only allowing http(s) / mailto), with no CDN dependency.

### 8.5 Replay pacing (`replay_timeline.dart` and `timeline` in `viewer.js`, with identical constants)

Ordered by the original timestamps, with long waits compressed and short ones kept:

1. The idle gap `g` between two segments: ≤ 500 ms kept as is, the excess × 0.2; capped at 1.6 s within a turn, and at 0.9 s before a question and before a turn starts (a person typing).
2. Entries overlapping something still running (parallel tool calls): appear 120–400 ms after the previous one, coming out in turn.
3. Replies: reasoning follows the original duration, clamped to 0.6–2.4 s; the body follows the original streaming duration, but no slower than 30 characters/second, no faster than 500 characters/second, at most 6 s and at least 0.3 s; with no duration it's estimated at 80 characters/second. Text appears character by character, with a cursor.
4. Tools: ≤ 300 ms kept as is, the excess × 0.15, clamped to 0.25–2.5 s; a spinner while running, the result shown when done.
5. A turn wraps up 150 ms after its last segment ends: collapse the process and show the footnote, like watching a turn end in chat.
6. Speeds 1× / 2× / 4× only change the clock speed; dragging the progress bar jumps straight to that moment (no animation); "Full text" jumps to the end and stops.

### 8.6 Hosted links

For the server side, the Dart client and "My shared links" see `docs/design/share-links.md`, and the interface is as the implementation in `services/share-worker/` defines. This section covers only the app side: the share panel's "Link": validity 7 days / 30 days (default) / permanent, and after generating, copy, QR code, share, stop sharing (undoable for 4 seconds after confirming, after which it's deleted from the server, the same path as deleting from "My shared links"), a line "End-to-end encrypted; the server can't see the content", and "My shared links" at the bottom of the page; what's uploaded is §8.1's file as is (UTF-8), gzip + AES-256-GCM encrypted by the client, with the key only in the link's `#k=`. In the app it goes through `conversationLinkMakerProvider` (`conversation_out.dart`, defaulting to the adapter in `ui/share_hosted/hosted_link_maker.dart`, with all generated links recorded in "My shared links"); when the provider is null the panel doesn't show "Link". A failed upload shows the sentence the client gives (network, too large, too frequent…). The viewer's decryption: `"DSG1"` + 12-byte IV + ciphertext (with tag), gunzipped after decryption and read per §8.1.

### 8.7 Opening in the app

`.dshgo` files (Open with / system share in) and `dshgo://share/…` links all go through `share_code_host.dart`: read the envelope first, and those whose body is `kind: conversation` go into "Conversation replay" (`replay_page.dart`), while the rest go into the import confirmation as before.

The replay page: top bar back · title · full text; below it a capsule: play / pause, progress bar, time, speed. The list is drawn with chat's own row components (`deriveRows` + the same row components and spacing), with images read from the file; the to-do and goal bars change with the replay moment. The primary button at the bottom, "Continue chat": creates a new chat, organizes this conversation into Markdown (questions, answers, one line per tool call; without reasoning and tool output) as an attachment, and prefills the composer with "Continue the conversation in the attachment:", to be edited by a person before sending. DSH has no interface for importing conversations, so the same conversation can't be continued as is.
