# C906: companion adaptation request, full replacement and mainline wiring

Base: `2ef25c07be4c63df15349ea491da6763da1b0528`. This round continues the original C810 (base `431bc52a647fbd587e29379e1f90ce92b409a484`), fixing its gap of treating the current alias as the post-replacement mapping. It is still the App-local adapter v1, reusing the existing stage capabilities; it is not passed off as the C720 market adapter v1. That the two formats share a name doesn't mean they share capabilities; a market upload should first convert and reject fields that can't be expressed.

## 1. Data shared by both modes

`companion_adapt_contract.dart` is a pure module with no I/O and no Flutter dependency. The original `companion_adapt.dart` re-exports it, so old callers needn't change imports. `companionAdaptInput` returns `{schema:"dsh-go/companion-adapt-request",v:1,target:"app-local-adapter-v1",vocabulary,probe,verifiedEffects,wanted,truncation,current?,currentDropped?,userFeedback?}`; `companionAdaptRequest` is its JSON string; `companionAdaptFullRequest` only prepends `/companion-adapt` to the same string.

`probe.mocFile` comes from the stage's relative path and is by no means a fingerprint. When the app saves, it still computes SHA-256 from the real moc3. Parameters are at most 800 usable records (the original request took only 600), names/groups at most 160 Unicode scalars, parts 300, expressions/motions 256 each; feedback 1000. Finite numbers, correct ranges and defaults are preconditions for entering the table. The stage reports raw min/max/default without three-decimal rounding, to avoid turning a very small but valid range into zero width. `parametersComplete` only says whether the parameter count is complete and can't be taken as semantic verification. When fields are truncated or excluded, the counts are explicitly kept; standard names that have no usable rule or identity evidence after replacement go into `coverageUnknown`.

The stage newly adds a complete `ruleAliasVersion: 1` and `ruleAliases: {standard name:{ids:[physical ID,...],scale,offset}}`, taken from `model.ruleAlias`, not from `model.alias` where the current adapter sits. The original order and duplicates of ids, finite non-zero scale and finite offset are all kept; nothing is recomputed from rounded ranges, and coefficients aren't guessed from `linked` which has only ids. The coefficients of existing rules aren't bound by the candidate params' 1000 cap. An old stage, an unknown version or any bad rule record makes the whole snapshot null, and a bad record must not be dropped and then wrongly prove that name has no rule; only an empty object proves an alias with no rules. A rule's target may still not be on the allowlist because of the 800 cap or protected metadata, and such a rule cannot support an automatic candidate.

`linked` is always only an observation of the current alias and may contain the old adapter that is about to be deleted; the request no longer fabricates a same-name identity for it. The rule snapshot is used only for validating the same model and the same probe/evidence this time; after the model changes or the evidence expires it must not be reused.

`CompanionAdaptEvidence` accepts only summaries of resource effects measured by the app or explicitly reviewed by a human: a map from exact loaded names to effect descriptions. It is a call parameter, not constructed from model replies, model names or the `probe`'s self-declared safe field. The existing stage produces no such measurements, so both maps are empty by default; loaded names can still be used for analysis but can't be executed. Future measurement must check parameter effects, show/hide, sound, events and side effects, and a screenshot or a name can't replace resource review.

## 2. Output fields and actual boundaries

| Field | App automatic adaptation this round | Difference from C720 or handling |
|---|---|---|
| adapter / moc | adapter may be omitted or 1; moc is added only when the app writes to disk | A model-fabricated fingerprint is not accepted; a path is not treated as a hash |
| params | Standard name → one ID or a list of co-driven IDs; shared scale/offset | C720 has only one target; a list can't be sent to the market directly, and the first item must not be taken silently |
| emotions.face | Smooth increments on standard channels supported by the effective mapping after replacement, clamped by semantic domain; EyeLOpen/ROpen later overridden by blinking are not accepted | Not an absolute pose; the current linked can't prove usability after replacement, and arbitrary native parameters or virtual eyelids are not opened |
| expressions / motions | Exact loaded names ∩ the app's verified-effects list | Merely being loaded, or names that look like happy or waving, are not enough; not opened by default |
| zones | Copies only existing coordinates in the report whose source is not default; xFrom/xTo in pairs | After the model matrix, before the camera; C720 has no x interval, and projection would lose horizontal separation |
| framing | This round's AI validation explicitly lists it in dropped | The base validation used to swallow it silently; to be opened after visible boundaries/camera facts and acceptance |
| tail | Actually existing, non-protected, and either registered or with metadata explicitly saying tail swing | The name is still only a candidate basis; arbitrary parameters can't be used to fake a tail |
| pose / toggles | AI candidates are not executed | Native pose and the market's toggles are not synonymous fields, and mechanical conversion is forbidden |
| notes | At most 60 Unicode scalars, one explanatory sentence | A local UI budget; the C720 market allows longer, which can't be inferred back as UI capacity |

An invalid explicit scale/offset rejects the whole item, rather than being changed to a default and executed. An id list with some unknown targets is also rejected as a whole item, avoiding silently becoming driving only one eye; duplicate IDs are deduplicated. Unknown top-level or nested fields are recorded in `dropped`, and an invalid/unknown version cannot be upgraded to v1. `zones:[]` can't turn off the base stage's default zones, so it is explicitly rejected rather than claimed to have turned them off. The automatic rejection of `framing`, `pose`, `toggles` and native face doesn't change the asset author's original character.json.

The criterion for full replacement is consistent with the actual `StageModel.adapt`. First construct the baseline from the complete rule snapshot: when a standard name has rules, all its targets must be in the effective physical list; if there are rules but the targets are unavailable, it can't fall back to the same-name identity. Only when the known rules truly don't contain that name and a same-name usable physical parameter exists can identity be used. Then overlay the candidate.params actually admitted this time; discarded candidate mappings don't participate in the proof. Finally admit only the face supported by this effective table. When the rules are unknown the baseline is empty, and face can rely only on explicit legal params of this run.

For example, the physical parameters have only `SmileShape`, the old adapter is `ParamMouthForm → SmileShape` with empty rules, and the new candidate has only `emotions.happy.face.ParamMouthForm=0.5`: that face must go into dropped, and the result is empty. The checker doesn't automatically copy the mapping from the old linked and doesn't fabricate scale=1; if the candidate explicitly keeps `id:SmileShape, scale:-2, offset:0.3`, then the actual set(0.5) is -0.7 and add(0.5) is -1. If the original rule had non-unit coefficients, omitting the old adapter override restores that rule's exact coefficients. An id list is a single-hop physical target and doesn't recursively resolve another standard name.

The protected-name filter is only an explicit-clue check, not a full semantic recognizer. New parameter mappings are still candidates proposed by the model, and the structural check can't recognize an arbitrary wrong effect hidden under an ordinary ID; the mainline still needs acceptance with the real stage. No new measurement was added, and this patch doesn't claim that "all unknown models are safely adapted".

## 3. Key prompt choices

All input is JSON-encoded; metadata, feedback and the existing table are all handled as data, so a name containing newlines or pseudo-instructions isn't spliced directly into an instruction line. The system text is stable, and the host skill reads the same prompt from `references/contract.txt`; `node tooling/companion/sync-adapt-skill.mjs --check` verifies they are verbatim identical.

It returns a complete replacement table; current is only a reference re-validated by the same checker and isn't merged automatically. Old adapter mappings that need to be kept must be given explicitly in this candidate's params with still-valid targets and original coefficients; omitting them deletes that override. Rules that still exist needn't be copied into the candidate params. The normal eye-open domain 0..1 isn't multiplied by two automatically because the model's maximum is 2; `set(v)=v*s+o`, `add(d)=current+d*s`, and increments don't add the offset. The current stage's EyeSmile mapping scale is 0..1, but dizzy still calls -0.5; the vocabulary states this fact explicitly and doesn't pretend to be fully consistent with C720's unified domain. L/R keep the model's marker, and angle direction is described as seen on screen.

Without geometry, don't make head, body or tail zones by human proportions; without resource effects, don't guess emotions from names like F01. Outputting only notes is allowed, and `companionAdapterEmpty` judges it as having no usable change; this isn't adaptation success, and no extra rounds are spent faking a result.

## 4. Mainline wiring and mounting

Lightweight mode still uses `companionAdaptAsk`, with the new request and validation wired in internally; the optional `evidence` must be held by the app. The same request and acceptance use the same probe/evidence snapshot, and late results are discarded after a model switch or package uninstall. The original host/asset ownership checks before writing to disk are kept.

Full mode has the page send `companionAdaptFullRequest(probe, note: ..., current: ..., evidence: ...)` in a separate technical session; don't put it into the companion chat backlog. After the text comes back: `companionAdaptJson` → `companionAdapterCheck(..., evidence: sameSnapshot)` → if non-empty, go through the existing `companionAdapterWrite` and the stage adapter command. An empty result keeps the old table. Don't let the host write phone files directly, and don't treat the host's metadata or replies as a new allowlist. Page wiring, cancellation, timeout and the scheduling of at most three rounds are not implemented in this patch.

The local skill is wired to three real entry points: the Flutter assets manifest, `extraSkillLoadersProvider`, and Kotlin `ManagedSkillRequest.names`. It keeps using the existing transactional install, engine generation and user-takeover rules: once the managed comment is deleted it isn't overwritten. A remote host loads `loadUiSkillBundle(null, companionAdaptSkillName)` only within an existing explicit install operation and hands it to `UiSkillRemoteInstaller.install(context, host, bundle)`; it can't install in the background just because it has the right to send messages. When an old host lacks the skill, lightweight mode may be chosen; to inline it in an ordinary technical session, send the same `companionAdaptSystem` and the same JSON report, with the app still validating, and without claiming the skill is installed.

`UiSkillRemoteInstaller` is currently an interface, the default provider is null, and this patch doesn't implement a remote-install UI. If the mainline prompts for installation through the relay, it can't directly reuse the existing `uiSkillInstallPrompt(bundle)`: it still fixes dsh-go-ui's directory and three files, which would miss this skill's `references/contract.txt`. Remote wiring must pass the complete `bundle.name/files` in an explicit user install operation and verify the install result; the existing `uiSkillShellScript(bundle)` generates the SSH script generically per bundle, but remote installation was not executed this round.

## 5. Verification and what the mainline still needs to accept

Pure Dart: `dart tooling/companion/check-adapt-contract.dart`; request generation/candidate validation: `dart tooling/companion/adapt-dry-run.dart probe.json [candidate.json]`. Cross-language replacement regression: `DART_BIN=/path/to/dart node --test tooling/companion/replay-adapt-replacement.test.mjs`; it executes the pinned Stage's real probeReport/fit/adapt/set/add and the real Dart checker, then feeds the returned adapter back into the real adapt and records the native API parameters, without simulating Core clamp or pixels. In the rule-range tests, a few explicitly marked rule-boundary fixtures set ruleAlias directly, while the rest are produced by the actual fitParams.

The parameter facts of the original public Haru/Wanko, the pinned official sources, inputs and outputs and logs are in C810-evidence.zip; both original cases were notes-only, empty=true, and can't be called two successful adaptations or a new AI experiment this round. No model, Core, texture or curve entered the patch. C904's 24-model historical parameter replay remains independent, updating an explicit SHA of the whole stage; reading the historical Core table doesn't mean the model was re-run or screenshots viewed this round.

The Flutter cases cover the existing lightweight request/disk write, the page request format and the local skill lifecycle; the Kotlin cases use the real installer to load all skill assets, compare every byte, and verify user takeover. Which were actually run this time is as stated in the independent review report with the exact patch SHA; Flutter tests that were written but not executed can't be counted as passing. Real user APIs, device WebView/GPU, pixel acceptance and the remote-install UI must all be separately verified by the mainline.
