# SQLite document code-point counting and peak indexing memory

Refs #444, #463, #476. Base v1.0.11 / 63e255fab5cb9d817af30b631c3643ccce8e9231, core 0.2.2-rc.1.

When SQLite session search first indexes or updates live / persisted documents, it computes the Unicode code-point length needed for ranking with `Array.from(text).length`. That expression builds a character array for the whole document, while indexing only uses the array's length. The patch computes the same result with a UTF-16 scan: starting from the code unit length, subtract one for each adjacent valid high/low surrogate found, skipping the already-paired low surrogate. A lone surrogate still counts as one; combining marks and ZWJ are still counted per code point, not changed to graphemes. Existing text cleaning, SQL parameters, ranking, paging, cancellation and persistence interfaces keep their original semantics.

Real public Context, SessionStore and SqliteSessionQueryEngine tests cover both the live and cold JSONL indexing paths, including ASCII, mixed Chinese/English, emoji, combining characters, lone surrogates and reserved-character cleaning; the original code-point count is used as an independent ranking golden, confirming page by page that there are no duplicates or omissions. The full-text array call count is only an allocation diagnostic and can't by itself prove a user-perceivable performance gain.

Measurements use the original patch 57 plus the already-delivered 665 and 688 as the control, to avoid mixing in their existing optimizations. AB/BA peak RSS for the first real search of a 4 MiB mixed document in independent new processes: control 201132 / 201072 KiB, candidate 162892 / 163032 KiB; pre-query peak 75260–75880 KiB, query increment control 125872 / 125512 KiB, candidate 87252 / 87152 KiB; the whole-process peak drops by about 37 MiB. This is the peak result for that Linux x64 / Node v24.22.1 process; it isn't the JS heap peak, nor a phone memory promise.

Total search latency fluctuates. With the final frozen source, one warm-up round and three sampling rounds per input per process, medians of the six AB/BA samples combined: 256 B 2.332→2.407 ms, ASCII 64 KiB 5.304→3.956 ms, emoji 64 KiB 6.065→5.397 ms, mixed 1 MiB 58.372→52.801 ms, mixed 4 MiB 236.680→219.379 ms. In an earlier independent AB/BA of a prototype of the same UTF-16 algorithm, 4 MiB was 218.478→231.252 ms, a regression. So this item only claims reducing the full-text character array and the peak RSS in that scenario, not a stable or general speedup; the complete positive and negative measurements are kept. The early for-of prototype wasn't adopted; its negative control is stored as separate evidence.

Changes runtimeVersion; upgrading replaces the user's runtime. Not compiled for Android; the full Flutter suite, app JVM, PRoot, ARM, real models and phone acceptance were not run. Real-device verification: on the same phone before and after upgrading, import or keep a large text session, search the same word for the first time, check results, ranking, continued paging and stopping the search; collect process memory and total time, and judge the trade-off between gain and latency from real-device results. No new dependencies or build configuration changes.
