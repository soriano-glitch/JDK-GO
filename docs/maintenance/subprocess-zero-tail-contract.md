# Subprocess cursor agreement for zero tail capacity (642)

This document records, before implementation, a correction for a regression introduced by the already-delivered 636 change. The base is public main's 63e255fab5cb9d817af30b631c3643ccce8e9231 (tag v1.0.11), DSH 0.2.2-rc.1. The release base doesn't include 636/637/638, and this package doesn't claim 1.0.11 itself has the regression. The read-only upstream `SubprocessCollect.maxBytes` doesn't forbid 0, and the public LocalSubprocessRuntime.spawn accepts `{maxBytes:0}`; Bash's own parameter validation can't replace this public service contract.

In the corresponding implementations of the original d935 and 1.0.11, after an ordinary Node outputs `abc`, readFrom(0) with zero tail capacity returns empty text, nextOffset=3, lossy=true. To keep the loss marker for "a positive-capacity tail containing only an incomplete UTF-8 prefix", 636 made empty and lossy reads not advance the cursor, but that also applied to a completely empty tail buffer, leaving nextOffset stuck at 0. There is real subprocess evidence that the original baseline passes and the 636+637+638 combination fails.

Minimal fix: at the start of readFrom, only when `this.bytes === 0`, return empty text, nextOffset=this.total, lossy=(fromByte < this.total), attaching spillPath per the original logic. On the release base 1.0.11 this branch keeps the existing values; combined with the delivered 636, 637 and 638 it corrects the regression. fromByte==total is still a non-lossy empty read, fromByte>total still returns total, and no cursor validation is added.

Positive capacity cases that actually keep incomplete UTF-8 bytes don't enter this branch: 636's pending/gap protection stays in effect. Zero tail capacity only means no in-memory text is kept; it doesn't forbid an existing complete spill artifact; the raw byte progress should be acknowledged both while active and after finishing.

The new independent runtime diff is ordered after 638's zsingle-read, without replacing or modifying frozen patches, adding public API/configuration or changing authorization. It changes runtimeVersion inputs; the version/pins are recorded locally through the existing process; this patch doesn't provide new pins. Verification uses its own Node, the public subprocess, and a real pipe/socket handshake; relying on sleep to create chunks is forbidden.
