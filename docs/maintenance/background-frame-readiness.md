# Background display first-frame readiness and secure windows

Refs #621, point 1 of #515. Near-black pixels don't prove FLAG_SECURE: an initially undrawn frame, an ordinary black screen and protected content can all be near-black. The current ImageReader background display capture has no reliable FLAG_SECURE detection source; the explicit secureWindow error priority is kept, and that existing branch is not described as a reliable detector.

One capture creates only one ImageReader, sets the surface once, and shares the original 2500 ms wait deadline. After a near-black first frame, the Image is closed first, then it waits briefly for at most 200 ms and no more than the remaining deadline, obtaining at most one extra frame; it doesn't repeat launch, tap, text, scroll or key, and doesn't read the whole tree again for the retry.

When it is known that no frame arrived by the deadline or both frames are still near-black, no screenshot or control content is output. A pure OP_OBSERVE returns frameNotReady; BackgroundDisplay's existing failed-read path clears old screen/element identifiers. An action already dispatched keeps its original OK result; the observation Bundle adds optional booleans frameNotReady=true, secure=false, n=0, with no image or element array; BackgroundDisplay produces an explicit "the screen isn't ready yet; later, only re-read the screen, don't replay the action just taken" snapshot, and clears old elements and the comparison cache at the same time. An old client that ignores the new fields still gets only 0 items and won't receive uncertain content.

IMAGE_OMITTED still only means the secret/control tree is incomplete and doesn't carry not-ready; the original complete tree, secret redaction and screenshot limits are kept. An explicit secure error still takes priority. Tree read errors follow the existing distinction between pure-read propagation and post-write observation being omittable, and are not rewritten by black frames; screenshot format/encoding faults are not classified as frameNotReady. Screenshot cancellation/interruption must exit immediately; other screenshot faults keep the original "no screenshot but a valid tree can still be read" semantics, neither pure reads nor post-write observations add a whole-call failure for these faults, and they are not marked frameNotReady. No new permissions, self-checks or FLAG_SECURE bypass.

The app JVM/Android was not run in this environment, and no first-red/final-green is claimed. The new pure policy is called by the production capture, and its Kotlin tests are only for local execution; compile failures on the old base due to the missing new API don't count as a semantic first red. A real device needs to compare the original and candidate on a normal app cold start, a persistently black screen, an explicitly protected page, cancel/release and action counts, recording the upper bound of the wait; don't fake results with a mirror implementation.
